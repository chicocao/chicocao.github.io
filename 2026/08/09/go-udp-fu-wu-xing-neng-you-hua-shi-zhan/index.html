Go UDP 服务性能优化实战

Go
发布日期:   2026-08-09
文章字数:   1.6k

压测一个 Go 写的 DNS 服务时，碰到一个挺反常的现象：机器有 24 个核，压测流量也加上去了，进程 CPU 却一直停在 1100% 左右，QPS 到 2.7 万附近后也不再明显增长。

一、问题背景

被压测服务运行在一台24核机器上。使用3台机器同时发送DNS请求，总QPS大约2.7万，但服务端CPU只能达到约 1100%，只使用了约11个核，操作系统层面的没有CPU限制。

二、CPU 火焰图没有达到最终效果

一开始只看了 CPU profile，能看到日志、网络系统调用和业务处理，去除不必要的日志等，然后再抓pprof，没有哪个函数足以解释为什么只用了 11 个核。后来把block和mutex profile一起抓了：

CPU profile    看正在消耗CPU的代码
block profile  看goroutine阻塞在哪里
mutex profile  看锁竞争在哪里

只看CPU profile很容易误判。例如，一个请求大量时间在等待锁，它不会一直出现在CPU火焰图的顶部，但它仍然会限制吞吐。

block和mutex默认是不开的，需要线下开启并压测看。

三、把请求解析移出 UDP 接收循环

原来的逻辑近似如下：

func (s *Server) receiveLoop(conn *net.UDPConn) {
    for {
        session, err := s.recvAndCreateSession(conn)
        if err != nil {
            continue
        }
        go s.handle(session)
    }
}

recvAndCreateSession 不只是收包，还会执行DNS解包、IP定位、配置查询和UUID创建。任何一步变慢，都会延迟下一次 ReadMsgUDP。

调整后，接收循环只负责收包和派发：

func (s *Server) receiveLoop(conn *net.UDPConn) {
    for {
        packet, err := s.recvOnce(conn)
        if err != nil {
            continue
        }
        go s.handlePacket(packet)
    }
}

func (s *Server) handlePacket(packet *udpPacket) {
    defer releaseUDPPacket(packet)
    // 可能会有耗时的操作
    session, err := NewSession(
        packet.data[:packet.n],
        packet.oob[:packet.oobn],
        packet.flags,
        packet.addr,
        packet.conn,
    )
    if err != nil {
        return
    }

    s.handle(session)
}

调整以后，收包协程做完 ReadMsgUDP 就能继续读下一个数据报，DNS解包、IP定位和配置查询不会再堵在它前面。

隐患：每个udp包都创建协程，goroutine会很高，可以考虑固定worker

四、使用 sync.Pool 复用收包对象

原始代码每次收包都会分配两个切片：

data := make([]byte, dns.MinMsgSize)
oob := make([]byte, 40)

高QPS下，这会产生大量短生命周期对象，增加分配和 GC 压力。优化后，将缓冲区直接内嵌到池对象中：

type udpPacket struct {
    data  [dns.MinMsgSize]byte
    oob   [40]byte
    n     int
    oobn  int
    flags int
    addr  *net.UDPAddr
    conn  *net.UDPConn
}

var udpPacketPool = sync.Pool{
    New: func() interface{} {
        return new(udpPacket)
    },
}

func acquireUDPPacket() *udpPacket {
    return udpPacketPool.Get().(*udpPacket)
}

func releaseUDPPacket(packet *udpPacket) {
    packet.n = 0
    packet.oobn = 0
    packet.flags = 0
    packet.addr = nil
    packet.conn = nil
    udpPacketPool.Put(packet)
}

读取时把数组转换成切片：

n, oobn, flags, addr, err := conn.ReadMsgUDP(
    packet.data[:],
    packet.oob[:],
)

4.1 为什么数组可以传给 ReadMsgUDP

packet.data[:] 不会复制数组，它只会创建一个指向原数组的切片描述符：

Data -> &packet.data[0]
Len  -> dns.MinMsgSize
Cap  -> dns.MinMsgSize

ReadMsgUDP 的参数类型仍然是 []byte，所以API语义没有改变。

4.2 ReadMsgUDP 会不会 append，导致底层数组变化

不会。

内核只知道一段地址和它的最大长度，不知道 Go 的 append、len 或 cap。因此它只会向调用方提供的内存写数据，不会分配新数组，也不会改变底层地址。

如果数据超过缓冲区，内核不会帮忙扩容，而是截断数据，并通过返回 flags。

五、删除热路径上的全局 sessionTable

服务原先为了在监控页显示“正在处理的 Session”，维护了一个全局 map：

s.Lock()
s.sessionTable[session.id] = session
s.Unlock()

defer func() {
    s.Lock()
    delete(s.sessionTable, session.id)
    s.Unlock()
}()

所有请求都会竞争同一把锁。block profile显示，约98%的阻塞都集中在这里。

这个功能只服务于一个低频监控页面，却让每个线上请求付出两次全局加锁的代价，收益和成本严重不匹配。最终删除 sessionTable 及对应监控展示。

六、单 UDP socket 也可能成为锁竞争点

删除 sessionTable 后，新的block profile显示约97.6%的阻塞转移到了：

internal/poll.(*fdMutex).rwlock
net.(*UDPConn).WriteMsgUDP

虽然Go允许多个 goroutine 并发调用 UDPConn，但同一个fd 的操作仍要经过内部同步。大量请求共享一个 UDP socket 回包时，写路径会争用同一个 fdMutex。

假设同时有 4 个请求：

请求 A ─┐
请求 B ─┼─> UDP socket fd=10 ─> WriteMsgUDP
请求 C ─┤
请求 D ─┘

但回包时，它们全部调用同一个：

internal/poll.(*fdMutex).rwlock
    net.(*UDPConn).WriteMsgUDP

这里的 conn 都指向 fd=10。

Go 为了保证同一个 fd 的并发操作安全，内部有 fdMutex。

于是在同一地址和端口创建多个启用了 SO_REUSEPORT 的UDP socket，让内核把流量分散到多个接收队列：

func udpListenerCount() int {
    if runtime.GOOS != "linux" {
        return 1
    }
    return runtime.GOMAXPROCS(0)
}

func listen(addr string) ([]*net.UDPConn, error) {
    count := udpListenerCount()
    conns := make([]*net.UDPConn, 0, count)

    for i := 0; i < count; i++ {
        packetConn, err := reuseport.NewReusablePortPacketConn("udp4", addr)
        if err != nil {
            return nil, err
        }

        conn, ok := packetConn.(*net.UDPConn)
        if !ok {
            _ = packetConn.Close()
            return nil, fmt.Errorf("unexpected conn type %T", packetConn)
        }
        conns = append(conns, conn)
    }

    return conns, nil
}

七、把每请求随机 UUID 改成进程前缀加原子序号

原实现每个请求都会生成随机 UUID：

id := uuid.NewV4().String()

在一次 98.06 秒 CPU 样本中，UUID 路径累计约 2.44 秒，占 2.49%。

主要开销不是字符串格式化，而是每个请求都进入系统随机数路径。

这个ID只用于日志关联，不参与鉴权、加密或业务随机决策，因此可以改为“随机前缀+原子递增序号”：

var (
    sessionIDPrefix = uuid.NewV4()
    sessionIDSeq    uint64
)

func newSessionID() string {
    id := sessionIDPrefix
    seq := atomic.AddUint64(&sessionIDSeq, 1)

    binary.BigEndian.PutUint64(id[8:], seq)
    id.SetVersion(uuid.V4)
    id.SetVariant(uuid.VariantRFC4122)
    return id.String()
}

这样每个进程只在启动时读取一次随机数，请求路径只需要：

  • 一次原子递增；
  • 复制 16 字节 UUID 值；
  • 一次 UUID 字符串编码。

最后

回头看，这次真正影响吞吐的不是某个业务算法，而是几处共享资源：全局 sessionTable、单个 UDP fd，以及后面的日志写入。UUID和对象分配也有成本，但量级比前面几项小。

所以排查顺序很重要。CPU profile 适合看时间花在哪，block 和 mutex profile 更适合回答“为什么没有更多代码在运行”。如果只盯着CPU火焰图，很可能会花很多时间优化一个占比两三个点的函数，却漏掉让大批 goroutine 等待的那把锁。
